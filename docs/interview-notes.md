# 悦选本地到家服务平台：后端面试要点

以下回答只覆盖仓库中已经实现的能力，不把课程练习或计划中的功能说成线上实践。

## 为什么 Redis SETNX 做幂等后还要数据库唯一索引？

Redis 的 `SETNX` 用于快速拦截短时间内相同 `Idempotency-Key` 的重复请求，减少重复进入数据库的概率。但 Redis 键会过期、Redis 可能故障，也可能出现两个请求跨过缓存窗口同时到达数据库。因此订单表还使用 `(user_id, submit_request_id)` 唯一约束作为最终兜底。发生并发冲突时，服务返回第一次创建的订单而不是创建第二单。

一句话：Redis 是高性能的前置闸门，数据库唯一索引才是跨故障、跨时间窗口的最终事实约束。

## 如何利用 MySQL 条件更新防止库存超卖？

下单不采用“先查库存再扣减”的两步写法，而是执行类似：

```sql
UPDATE product_sku
SET stock = stock - :quantity
WHERE id = :skuId AND status = 1 AND stock >= :quantity;
```

只有影响行数为 `1` 才表示库存扣减成功；影响行数为 `0` 代表库存不足或商品已下架。订单、明细、库存扣减在同一个本地事务中，任一组成 SKU 扣减失败时整个组合订单回滚。取消、超时关闭和拒单按照订单明细回补相同 SKU 库存。

## 幂等、限流、分布式锁的区别是什么？

| 概念 | 解决的问题 | 本项目位置 |
| --- | --- | --- |
| 幂等 | 同一个业务请求重复执行，结果仍然只有一次 | `Idempotency-Key`、订单唯一索引、支付状态条件更新、消息事件去重 |
| 限流 | 在一段时间内限制请求数量，保护系统 | Redis Lua：同一用户 60 秒最多提交 5 次订单 |
| 分布式锁 | 多节点竞争同一临界资源时让同一时刻只有一个持有者 | 当前下单库存不依赖分布式锁，而是用 MySQL 条件更新；Outbox 通过条件更新抢占事件 |

不能把它们混为一谈：限流不能保证订单不重复，幂等不能限制恶意高频请求，分布式锁也不能替代数据库库存条件。

## Outbox 模式解决什么问题？失败重试和消息幂等如何处理？

订单支付成功后，如果先提交数据库再直接发送 MQ，应用可能恰好在两者之间宕机，出现“订单已支付但运营端永远收不到通知”。本项目在同一 MySQL 事务里写订单状态和 `outbox_event(PENDING)`，后台 `OutboxDispatchTask` 再扫描、抢占并投递 RabbitMQ。

投递失败会记录失败原因，递增重试次数，并按指数退避安排下一次投递；发送卡在 `SENDING` 的事件可被重新调度。RabbitMQ 是至少一次投递，可能重复，所以消费者使用 `processed_message(event_id, consumer_name)` 唯一键去重；超时关单还使用 `WHERE status = 待支付` 的条件更新，只有实际变更状态的执行者才回补库存。

## Cache Aside 的读写流程、失效策略和可能的不一致窗口？

用户浏览商品时先按分类读取 Redis Key `yuexuan:v2:product:list:{categoryId}`；命中直接返回，未命中再查 MySQL，并用带随机抖动的 TTL 回填缓存。管理端商品新增、编辑、上下架或删除后精确删除相关分类 Key，下一次读取自动回源。

不一致窗口仍然存在：数据库更新提交到缓存删除之间、或缓存删除失败时，用户可能在 TTL 结束前读到旧数据。当前选择的是简单可靠的 Cache Aside；后续可用消息重试、版本号或更严格的缓存一致性方案增强。

## TraceId 如何在一次请求中串联日志？

`TraceIdFilter` 从 `X-Trace-Id` 读取合法值，或为请求生成 `yx-...` 标识，写入 MDC 并回写到响应头。日志格式包含 `[traceId=%X{traceId:-}]`，因此过滤器、JWT 鉴权、限流、订单服务和异常日志可通过同一个 TraceId 串起来。排查一次下单时，可以从响应头复制 TraceId，再在日志中搜索该值。

## 项目中我会主动说明的限制

- 没有虚构压测 QPS、线上订单量或生产规模；当前是本地可运行的项目化实践。
- RabbitMQ Confirm、手动 ACK、重试、DLQ、Outbox 和消费幂等都有代码与测试，但真实生产监控告警尚未完成。
- 小程序目录是编译产物，当前重点是业务闭环与接口适配，前端源码重建是下一阶段工作。
