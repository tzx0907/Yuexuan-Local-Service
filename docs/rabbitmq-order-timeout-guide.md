# RabbitMQ 实战二：15 分钟未支付订单自动关闭

这一阶段解决的问题是：用户创建订单时已经占用了库存，但一直不支付，系统不能永久为他保留库存。订单超过 15 分钟仍未支付时，系统需要自动关闭订单，并把本次占用的商品库存还回去。

## 一、为什么不能在下单接口里等待 15 分钟

最直观但错误的写法是：创建订单后让当前线程 `sleep(15 分钟)`，然后检查订单。

这样做会长期占用 Web 请求线程和数据库等资源。只要同时有很多未支付订单，服务就会很快没有线程处理新的请求；应用重启后，等待中的任务还会全部丢失。

RabbitMQ 的作用是把“现在创建订单”和“15 分钟后检查订单”拆开：

```text
用户提交订单
    ↓
数据库事务提交成功（订单和明细已经保存、库存已经扣减）
    ↓
发送一条关单事件到延迟队列
    ↓
消息在队列里等待 15 分钟
    ↓
转入真正的关单队列
    ↓
消费者检查订单当前状态
    ├─ 已支付：忽略消息
    ├─ 已取消：忽略消息
    └─ 仍待支付：取消订单，并在同一事务中回补库存
```

Web 请求无需等待，RabbitMQ 负责保存这份“稍后再做”的工作。

## 二、TTL 和死信为什么能实现延迟消息

### 1. TTL 是什么

TTL（Time To Live）表示消息可以在队列中存活多长时间。本项目为延迟队列配置：

```java
x-message-ttl = 15 * 60 * 1000
```

消息进入 `yuexuan.order.close.delay.queue` 后会存活 15 分钟。这个队列故意没有消费者，因此消息不会被提前取走。

### 2. 死信是什么

消息过期、被拒绝或队列达到限制时，会成为“死信”。如果队列配置了死信交换机和死信路由键，RabbitMQ 会把它重新投递到指定交换机。

本项目利用“过期成为死信”实现延迟：

```text
yuexuan.order.close.delay.queue
    -- TTL 到期 -->
yuexuan.order.event.exchange（routing key = order.close）
    -->
yuexuan.order.close.queue
```

这里的死信不表示业务失败，只是借用了 RabbitMQ 的死信转发能力做 15 分钟延迟。

真正因消费连续失败产生的消息，则进入另一个队列：

```text
yuexuan.order.close.dlq
```

因此，“延迟所用的死信转发”和“失败消息最终进入 DLQ”是两个不同用途。

## 三、各个类的关系

### `RabbitMqConfig`

它声明 RabbitMQ 中的交换机、队列、绑定关系、15 分钟 TTL、手动 ACK、重试次数和失败 DLQ。它相当于整套消息通道的装配图。

### `OrderCloseEvent`

它是消息正文，保存：

- `eventId`：本次事件的唯一编号；
- `orderId`：需要在 15 分钟后检查的订单；
- `orderNumber`：便于日志排查；
- `createdAt`：事件创建时间；
- `closeAt`：计划检查时间。

消息只携带定位和排查所需的信息，不把订单当时的完整状态当成最终依据。

### `OrderCloseEventPublisher`

它是生产者。订单数据库事务成功提交后，它把 `OrderCloseEvent` 投递到延迟队列。

必须在事务提交后发送：如果数据库最终回滚却已经发了消息，15 分钟后消费者会收到一条对应不存在订单的无效消息。

当前阶段如果 RabbitMQ 暂时不可用，发布失败只记录日志，不让已经创建成功的订单对用户显示失败；定时任务会兜底。下一阶段 Outbox 会进一步解决可靠投递问题。

### `OrderCloseConsumer`

它监听真正的关单队列。收到消息后不直接改数据库，而是调用 `OrderTimeoutService`，业务成功后才手动 ACK。

### `OrderTimeoutServiceImpl`

所有自动关单的核心规则都集中在这里。RabbitMQ 消费者和定时任务都调用它，避免两套关单代码逐渐产生不同规则。

它按以下顺序执行：

1. 查询订单，确认它仍是待支付且未支付；
2. 使用带状态条件的 SQL，把订单从待支付改为已取消；
3. 只有条件更新成功的执行者，才读取订单明细并回补商品或 SKU 库存；
4. 取消订单和回补库存位于同一个数据库事务中，任何一步失败都会整体回滚。

### `OrderTask`

它是定时兜底任务。如果 RabbitMQ 停机、网络中断或消息未成功发送，定时任务仍会扫描超时订单，并调用同一个 `OrderTimeoutService`。

RabbitMQ 提供接近 15 分钟的及时处理，定时任务提供故障兜底，两者不是互相替代关系。

## 四、为什么消息到期后还必须重新查询订单

事件表达的是“15 分钟后请检查这个订单”，而不是“15 分钟后无条件取消这个订单”。

在这 15 分钟内，用户可能已经支付。消息内容是创建订单时的历史快照，数据库才是当前真实状态。因此消费者必须做二次检查：

```java
订单仍是待支付 && 支付状态仍是未支付
```

如果已经支付，消费者正常结束并 ACK，绝不能取消订单或回补库存。

## 五、为什么要使用条件更新

仅仅“先查询，再更新”仍不够安全。可能发生：

```text
MQ 消费者查询：待支付
定时任务查询：待支付
MQ 取消并回补库存
定时任务也取消并再次回补库存
```

项目使用：

```sql
UPDATE orders
SET status = 已取消, ...
WHERE id = ? AND status = 待支付
```

第一个执行者更新成功，影响行数为 1；第二个执行者再执行时条件已经不成立，影响行数为 0。代码规定只有影响行数为 1 的执行者才能回补库存。

这个条件更新就是幂等闸门，它同时防住：

- RabbitMQ 重复投递；
- 消费者和定时任务并发；
- 多个应用实例同时消费或扫描；
- 消费完成但 ACK 丢失导致的再次投递。

## 六、ACK、重试和 DLQ 分别解决什么

### 手动 ACK

ACK 是消费者告诉 RabbitMQ：“这条消息已经处理完成，可以删除。”

本项目只在业务方法正常完成后调用 `basicAck`。如果数据库操作抛异常，不发送 ACK，避免消息在业务失败时被当作成功删除。

### Retry

数据库瞬时抖动或网络短暂异常可能很快恢复，所以消费者失败后会按退避策略最多尝试 3 次，而不是第一次失败就永久放弃。

### DLQ

如果 3 次仍失败，消息被拒绝并进入 `yuexuan.order.close.dlq`。DLQ 保存无法自动处理的异常消息，便于报警、排查和人工补偿，避免无限重试拖垮系统。

## 七、为什么取消和回补库存必须在同一事务中

如果订单已取消但库存没有还回去，会产生库存无故减少；如果库存已还回但订单仍待支付，用户随后又支付，就可能卖出并不存在的库存。

所以这两个动作必须原子化：

```text
取消订单成功 + 全部明细库存回补成功 = 提交事务
任一库存回补失败                         = 整体回滚
```

带 `skuId` 的明细回补 `product_sku.stock`；没有 `skuId` 的普通商品回补 `dish.stock`。不关联商品或 SKU 库存的明细不执行库存回补。

## 八、这一版的可靠性边界

这一阶段已经具备：延迟关单、支付状态二次检查、条件更新幂等、事务库存回补、手动 ACK、消费重试、失败 DLQ和定时任务兜底。

但“数据库事务已提交”和“消息已成功发送”仍是两个独立动作。如果恰好在两者之间宕机，延迟消息可能没有发出，当前由定时任务兜底，及时性会受扫描周期影响。

下一阶段使用 Outbox：在创建订单的同一个数据库事务中写入一条待发送事件，再由后台任务可靠投递到 RabbitMQ。这样可以把“订单已创建但消息没有任何记录”的窗口进一步消除。

3. 为什么消息到期后必须重新查数据库；
4. `WHERE status = 待支付` 如何防止重复关单和重复回补；
5. 为什么订单取消和库存回补必须在同一事务；
6. 手动 ACK、Retry、DLQ 各自解决的问题；

8. 当前方案为什么还需要 Outbox。

能结合本项目完整回答这些问题，并能顺着“生产者 → 交换机 → 延迟队列 → 死信转发 → 关闭队列 → 消费者 → 业务事务 → ACK”找到相应代码，就已经达到了实习面试中对 RabbitMQ 基础项目经验较扎实的程度。
